# 02 · 补丁源表规则

[规则顺序](README.md) · 上一步：[01 项目清单](01-game-project.md) · 下一步：[03 表字段](03-table-schemas.md)

本文说明公开翻译表的稳定身份、修改和审计要求。翻译表用于把经过审核的目标语言文本绑定到游戏资源，不是为了阅读而随意整理的台词导出。不同引擎已有不同字段，不能把某个游戏的 CSV 当成全仓库统一格式。

## 位置与语言边界

公开翻译表按引擎与游戏归档：`AGE2/games/<game>/translations/` 或 `rUGP/games/<game>/translations/`。不同游戏和目标语言必须拥有独立文件与发布身份；新语言流程见 [`../new-locale.md`](../new-locale.md)。

所有表都应能持久定位到原资源，通常需要：

- 游戏与受支持版本；
- 稳定行/记录 ID，或可验证的资源身份；
- 来源容器、资源文件、场景或路由信息；
- 目标语言文本；
- 影响序列化的控制符、容量或运行时绑定信息（若该格式需要）；
- 足以检测源版本漂移的哈希或其他证据。

具体字段由对应游戏的 README、builder 和测试共同定义。`cn_text`、`zh_cn`、`translation_text` 等是现有简体中文表的历史字段名，不是新语言必须照抄的统一 schema。

## 日文原文与公开边界

- AGE2 的五张大型公开正文表保留有限的说话人/场景上下文，但以 `source_text_sha256` 代替完整日文正文。普通记录标为 `record_kind=text`；只有源、说话人与目标均为空的引擎结构槽才标为 `record_kind=structural_empty`，由 builder 验证后跳过。其他小型界面/图片文案表是否可含来源字段仍需逐表审核。
- rUGP 的两张 69/151 行运行时表保存偏移、容量、控制与绑定合约；四张共 57,547 行的审校表只保存稳定身份、RIO/scene、源字段哈希和译文，仍需另行绑定到安全写入路线。两类表都不公开完整日文台词；合法持有者应从受支持的本地游戏版本重新验证身份。
- 英文槽、旧翻译和模糊匹配可以用于发现问题，但不能替代 JP 原文成为翻译含义的权威来源。

因此，“所有公开表都必须包含 `speaker_jp` / `jp_text`”并不是仓库规则。能否公开源文本取决于游戏、来源和[内容与发布政策](../../docs/project/asset-and-release-policy.md)。

## 修改规则

- 只修改明确目标游戏、章节和语言的表。
- 保持稳定定位字段与受支持源版本对齐；发现哈希或行身份漂移时停止写回。
- 不修改作为证据保留的源字段、原始控制信息和稳定 ID。
- 目标文本的控制符按对应引擎规则处理，不把 JP 换行标记无条件复制过去。
- 保留原文引号、括号等功能；若目标语言需要改写形式，应在语言规范中说明。
- 不因某一文本槽看起来为空就删除台词，必须先证明游戏实际使用的槽或运行时绑定。
- 修改前确认该游戏 schema 要求的 ID、资源、场景、源证据和目标文本字段。

## 审核字段

可长期解释发布状态的字段（例如 `review_status`、审核人、冻结版本或可复现的 `audit_flags`）可以进入公开表，并应由测试约束。一次性脚本列、个人路径、临时排序、模型原始输出和无法复现的便签应留在本地工作区或转化为正式问题记录。不要为了追求“纯两列表”而删除仍被 builder 或审计流程使用的稳定字段。

## 修改后 QA

修改后至少检查以下内容；资源写回和打包的完整要求见 [`AGE2`](../../AGE2/docs/quality.md) 或 [`rUGP`](../../rUGP/docs/quality.md) 质检文档：

- 稳定 ID、源哈希、记录数量和顺序是否与声明版本一致；
- 必填目标文本是否为空，是否存在重复、乱码或编码损坏；
- 非预期的英语整句、日文假名或其他源语言残留；
- 控制符、UTF-16 容量、换行和终止符是否符合目标资源格式；
- 说话人、人名、军衔和术语一致性；
- builder 实际读取的列、资源和语言是否就是本次审核的版本。

格式检查不等于端到端证明。最终补丁仍需按引擎完成构建、清洁安装、实机、卸载/回滚与发布清单验证。Release 载荷不应作为生成物提交回源码目录；公开资产是否能进入仓库则按资产政策逐项判断。
